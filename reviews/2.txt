Below is a thorough review based on the current codebase. I focused on core SQL generation, query planning, and the three main drivers (MySQL, Postgres, SQLite), then highlighted potential issues and optimization opportunities. I’ve included citations for all claims based on the files reviewed.
Scope Reviewed

    Query planning and SQL compilation logic (core QueryGrammar and _SelectCompilation).

    MySQL grammar and connector behavior.

    Postgres grammar and connector behavior.

    SQLite grammar and connector behavior.

Key Findings & Potential Issues
1) Group-limit relies on window functions without driver/version gating

    The SQL generator emits ROW_NUMBER() OVER (...) for group limits, and then wraps the select with filters on the generated row number.

    QueryGrammar.supportsGroupLimit defaults to true, and MySQL’s grammar does not override it, which means MySQL/MariaDB could emit window function SQL on versions that don’t support it (MySQL < 8, older MariaDB).

    SQLite does gate it behind supportsWindowFunctions, but the driver doesn’t appear to auto-detect SQLite version, so older SQLite versions could still break at runtime unless configured correctly.

Recommendation: Add capability/feature checks (or version detection) in driver adapters so group limit is only enabled when the runtime DB actually supports window functions.
2) Auto-hydration can inflate select lists and force aggregates

    When a query uses custom projections, Ormed automatically adds extra “hydration” columns (often all model fields not already selected).

    In grouped queries, this auto-hydration uses MIN(column) to keep SQL valid, which can distort semantics and adds extra aggregate work (potentially large).

Recommendation: For aggregate-heavy queries, prefer explicit projections and disable auto-hydration to avoid extra columns and aggregation work.
3) Driver session options are interpolated directly

    Postgres applies SET <key> = <literal> with <key> coming from user-supplied options without sanitization/whitelisting; the value is quoted, but the key is not.

    SQLite does PRAGMA <key> = <value> with the key coming from user-supplied session options, again without sanitization (value is quoted).

    MySQL session variables use @@key = literal with keys from the config; values are quoted safely but keys are not validated.

Recommendation: If session options are ever user-controlled, add allowlists/validation for option keys to prevent SQL injection via the key name.
4) Postgres full-text language value is inlined

    The Postgres full-text compiler inserts the language string directly into SQL without parameterization (e.g., to_tsvector('$language', ...)).

Recommendation: Validate language against a known list or otherwise sanitize it if the value can be influenced externally.
5) LATERAL joins enabled for MySQL unconditionally

    MySQL grammar reports supportsLateralJoins => true, but MariaDB and older MySQL versions can lack LATERAL support.

Recommendation: For MariaDB (and older MySQL), consider gating LATERAL support to prevent runtime errors.
SQL Optimization Opportunities
1) Avoid auto-hydration overhead for large/aggregate queries

    Auto-hydration adds extra select columns and sometimes MIN() aggregates; this can add sorting/aggregation work and widen result sets.

    Optimization: When possible, select explicit columns only, or disable auto-hydration on aggregate queries.

2) Use driver-specific features to reduce sorts/joins

    Postgres supports DISTINCT ON and the grammar explicitly compiles it when configured in QueryPlan (when distinctOnExpressions is populated).

    Optimization: Prefer DISTINCT ON for “first row per group” patterns instead of window functions when it aligns with your requirements.

3) Index hint support in MySQL

    MySQL grammar supports USE/FORCE/IGNORE INDEX hints and compiles them when present in the plan.

    Optimization: Consider index hints for known-heavy queries to reduce suboptimal plans.

4) JSON predicates can bypass indexes

    JSON predicate compilation uses JSON_EXTRACT/json_each/jsonb operations depending on the driver; these frequently prevent index use unless using generated columns or expression indexes.

Optimization: For hot paths, consider indexed generated columns or schema changes that materialize commonly filtered JSON fields.
Driver-Specific Notes
MySQL

    OFFSET without LIMIT is compiled as LIMIT 18446744073709551615 OFFSET ?, which is correct for MySQL but can be heavy on large tables.

    Window functions are implicitly relied on for group limits (see issue above).

Postgres

    Full-text search inlines the language value in SQL (see issue above).

    JSON predicate logic uses jsonb casts and operators; good for correctness but can be heavy without indexes.

SQLite

    supportsWindowFunctions defaults to true; if SQLite is older, group-limit queries may fail unless overridden.

    Full-text search relies on external FTS tables using naming conventions (good, but requires migrations to build the FTS tables).
