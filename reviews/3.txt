Summary

    Completed a code-level review of the core query compiler, cache, and the SQLite/MySQL/Postgres driver adapters to surface risk areas and SQL-generation optimization opportunities.

Review Findings & Potential Issues
Cross-cutting / Core

    Query cache has no automatic invalidation on writes — cache entries are stored and served strictly by SQL+bindings/TTL, with manual flush/vacuum only, so mutations can lead to stale reads unless the caller explicitly clears cache or uses short TTLs.

    Raw SQL interpolation lint is warning-only — the static rule flags interpolation without bindings, but it is only a WARNING and limited to a specific set of raw methods, so misuse can slip through at runtime if linting isn’t enforced in CI/CD.

SQLite Driver

    stream() is not truly streaming — the implementation materializes all rows into memory, decodes them, and then yields, which defeats backpressure and increases memory use on large result sets.

    Random order is applied twice — SQL compilation already injects ORDER BY RANDOM() when randomOrder is enabled, and the SQLite adapter then re-shuffles the in-memory result set, which adds overhead and can distort randomness distribution.

    rowid is assumed for query updates/deletes — the adapter uses rowid as the row identifier, which will fail for WITHOUT ROWID tables or certain views.

    RETURNING is always advertised — SQLite supportsReturning is set to true and SQL emits RETURNING clauses when requested, but there is no version gating; older SQLite versions will error on these statements.

MySQL/MariaDB Driver

    Capability mismatch for RETURNING — driver metadata advertises DriverCapability.returning, yet the driver explicitly documents that MySQL/MariaDB don’t support native RETURNING and that it’s ignored for update/delete/upsert. This can surprise callers expecting a real RETURNING clause and lead to inconsistent behavior across drivers.

Postgres Driver

    Placeholder scanning is naive — _formatPreviewSql treats every ? as a placeholder, which can break if raw SQL contains ? as a literal/operator (e.g., JSONB ? operator), leading to mismatched placeholder counts or incorrect previews.

SQL Generation: Optimization Opportunities

    Relation aggregates and whereHas rely on subqueries/EXISTS — relation aggregates are compiled into subqueries and predicates use EXISTS/NOT EXISTS. This is correct but can be heavy on large datasets; consider optional join-based aggregation or precomputed materialized views for hot paths, especially for count/sum/avg on large relations.

    Random ordering cost — random ordering is pushed into SQL and (for SQLite) additionally shuffled in memory, which is expensive for large datasets. Consider avoiding random ordering in hot paths or implement a lightweight sampling strategy when possible.

    Cache strategy — since cache invalidation is manual, it’s best used for read-mostly paths or time-bounded reads; heavy mutation flows should either disable caching or flush on write to avoid serving stale SQL results.
